# T1110.003: Brute Force - Password Spraying

## 📋 Technique Overview

| Attribute | Value |
|-----------|-------|
| **Technique ID** | T1110.003 |
| **Technique Name** | Brute Force: Password Spraying |
| **Tactic** | Credential Access (TA0006) |
| **Sub-technique of** | T1110 (Brute Force) |
| **Platform** | Linux, Windows, macOS, Network Devices |

## 🎯 Attack Description

Password spraying is a brute force credential attack where adversaries try a **small number of commonly-used passwords** against **many different accounts** to avoid account lockout policies.

**Key Characteristics:**
- **Low & Slow:** 1-3 password attempts per account
- **Wide Targeting:** Hundreds/thousands of accounts
- **Lockout Evasion:** Stays below failed login threshold
- **Common Passwords:** "Password123!", "Summer2024!", "Company@123"

**Attack Flow:**
```
Step 1: Enumerate usernames (OSINT, LinkedIn, leaked databases)
Step 2: Select common passwords (top 5-10)
Step 3: Try password #1 against ALL users
Step 4: Wait 30 minutes (avoid detection)
Step 5: Try password #2 against ALL users
Step 6: Repeat until successful authentication
```

## 🔍 Detection in Our Lab

### Snort Rule (Portfolio 2)
```
alert tcp any any -> $HOME_NET 22 (
    msg:"SSH Brute Force Detected"; 
    threshold:type limit, track by_src, count 5, seconds 60; 
    sid:1000002; 
    rev:1;
)
```

**Detection Logic:**
- Monitors SSH authentication attempts (port 22)
- Triggers when same source IP has 5+ failed attempts within 60 seconds
- `track by_src`: Counts independently per attacker IP

### Wazuh SIEM Rule (Portfolio 4)
```xml
<rule id="100002" level="10">
  <if_group>authentication_failed</if_group>
  <match>Failed password|authentication failure</match>
  <same_source_ip />
  <different_user />
  <options>no_full_log</options>
  <description>Password spraying attack detected (T1110.003)</description>
  <mitre>
    <id>T1110.003</id>
  </mitre>
</rule>
```

**Detection Logic:**
- Correlates failed authentication logs across endpoints
- Triggers when same IP fails authentication for multiple different usernames
- Maps to MITRE T1110.003 for threat intelligence context

## 🛡️ Mitigations

### M1027: Password Policies (Primary)

**Implementation:**
```bash
# Enforce strong passwords in /etc/security/pwquality.conf
minlen = 14
minclass = 3
maxrepeat = 2
maxclassrepeat = 4
```

**Policy Requirements:**
- Minimum 14 characters
- 3 character classes (uppercase, lowercase, numbers)
- No common dictionary words
- No repeated characters (e.g., "aaa")

### M1032: Multi-Factor Authentication (Critical)

**Why MFA Defeats Password Spraying:**
- Even if attacker guesses password, cannot bypass 2nd factor
- OTP codes (Google Authenticator, Duo) expire in 30-60 seconds
- Hardware tokens (YubiKey) cannot be remotely stolen

**Implementation Example:**
```bash
# Enable Google Authenticator for SSH
sudo apt install libpam-google-authenticator

# Configure PAM
echo "auth required pam_google_authenticator.so" | sudo tee -a /etc/pam.d/sshd
```

### M1036: Account Use Policies

**Progressive Lockout:**
```python
# Pseudocode for intelligent lockout
failed_attempts = 0

def authenticate(username, password):
    if failed_attempts >= 3:
        lockout_duration = 15 * (2 ** (failed_attempts - 3))  # Exponential backoff
        sleep(lockout_duration)
    
    if is_valid(username, password):
        failed_attempts = 0
        return True
    else:
        failed_attempts += 1
        return False
```

**Lockout Schedule:**
| Attempt # | Lockout Duration |
|-----------|------------------|
| 1-3 | No lockout |
| 4 | 15 seconds |
| 5 | 30 seconds |
| 6 | 60 seconds |
| 7+ | 5 minutes |

### Additional Mitigations

**1. Account Naming Standards:**
```
❌ Bad: firstname.lastname@company.com (easily guessable)
✅ Good: f.lastname.12345@company.com (adds entropy)
```

**2. Monitoring & Alerting:**
```bash
# Alert on failed logins from same IP to multiple accounts
SELECT source_ip, COUNT(DISTINCT username) as unique_users
FROM auth_logs
WHERE status = 'failed'
GROUP BY source_ip
HAVING unique_users > 5
```

**3. Geolocation-Based Blocking:**
```
# Block authentication from high-risk countries (if no legitimate users there)
if user_ip_country in ['RU', 'CN', 'KP'] and user_country != user_ip_country:
    alert_security_team()
    require_additional_verification()
```

| Indicator | Confidence Level |
|-----------|-----------------|
| Same IP, multiple failed auths | 🟢 HIGH (95%) |
| Same IP, multiple usernames | 🟢 HIGH (90%) |
| Multiple IPs, single username | 🟡 MEDIUM (60%) |
| Low frequency (< 5 attempts/hour) | 🔴 LOW (30%) |

**Why Low Frequency is Hard to Detect:**
- Adversaries can space attempts over days/weeks
- Blends in with legitimate failed logins (typos, forgotten passwords)
- Requires long-term statistical baseline
